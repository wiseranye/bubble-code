# 会话压缩：追加压缩条目到会话文件，恢复时按条目投影上下文

上下文超长时需要压缩。我们选定的形态：会话文件保持 append-only，压缩落盘为尾部追加的 `compaction` 条目 `{ summary, summarizedCount, firstRetainedEntryId }`，原始消息一律不删；恢复时以最后一条压缩条目为准，协议历史投影为 system + 摘要（重新生成 user 消息）+ 从 `firstRetainedEntryId` 起的保留区间 + 压缩后新增的消息，转录区则重放全部消息、在压缩点插入永久标记——压缩只影响发给模型的 Context，从不销毁用户的阅读记录。切点用条目 id 而不用条数：id 对重排、重复、人工编辑文件都稳健，条目本就有 uuidv7，零额外成本；`summarizedCount` 不参与投影，仅供 UI 提示「前 N 条已摘要」。摘要调用是侧信道（`ModelApi.stream` 递归，不带 system prompt 与工具），请求与响应都不进历史，第二次压缩把上一次摘要作为输入合并，被摘要的消息永不回流。摘要作为带固定前缀的 user 消息放在投影头部，对所有 provider 都安全。用量测量锚定最近一次 `AssistantMessage.usage` 的真实计数，其后消息按字符数/4 估算；阈值（0.8）与保留比例（0.16）相对 contextWindow，settings 顶层可配。压缩检查在每个 turn 的请求之前（`runAgentLoop` 的 `beforeRequest` 回调，含第一轮），超阈值就地在循环内压缩，压缩条目按发生时刻追加进文件、排在已持久化的 turn 条目之后；回调返回替换后的完整消息列表，循环原地替换运行上下文并剔除 newMessages 中被摘要的前缀，`state.messages` 只接收投影中属于原 state 的部分，run 新增消息仍由 run 结束时统一 push。手动压缩（/compact）忽略阈值且没有长度守卫：保留预算装得下全部消息时，回退为只保留最后一轮（摘要到最后一条 user 消息为止）。

**考虑过的选项**：切点记「被摘要条数」更省一个字段，但条数依赖条目顺序绝不被扰动，id 是自描述引用，损坏时可探测（找不到 id 就忽略该压缩条目、保留全部消息，宁可丢摘要不丢上下文）；物理重写文件把摘要放在保留区间之前可以让投影规则更简单，但破坏 append-only 与写入队列的既有一致性假设；摘要放 system prompt 对 OpenAI 系协议的位置支持不一，user 消息最通用；turn 中途（工具循环内）只打标、run 结束再压曾被采用，但长工具循环中途就会超窗口、下一个请求直接被 API 拒绝，阈值预留的 20% 余量吸收不了，否决，改为每个 turn 的 stream 之前检查并在循环内压缩。

**后果**：旧会话文件没有压缩条目，恢复路径自然兼容；新文件被旧版本读取的行为不保证（项目未发稳定版）。`SessionManager.appendMessage` 改为返回条目 id，AgentSession 以 WeakMap（消息对象 → 条目 id）维护映射，依赖 turn_end 事件与 `state.messages` 持有同一对象引用这一事实；run 的 user 消息也由 AgentSession 构造、登记后再传入 runAgentLoop，循环内压缩的切点落在它上面时同样拿得到 id。自动压缩失败后闭锁，直到新一轮产生真实 usage 再解除，避免每轮重复失败的提示风暴。摘要用的模型暂固定为当前会话模型，可配置摘要模型留作待办。
