# ADR-005: 系统提示词动态刷新：钩子触发、按生产顺序追加、发送视图只取最新

- **Status:** Accepted
- **Date:** 2026-10-22

## 背景

系统提示词原本只在会话建立时构造一次（`Agent` 构造函数），之后不再变化。问题：会话中途新增工具、以后接入 MCP / Skill 等扩展能力，或升级 CLI 后 resume 老会话时，进行中的会话感知不到这些变化。约束：

- 会话文件是 append-only JSONL，内存与会话文件都按生产顺序排列（ADR 0004 的一致性假设）。
- 项目经 pi-ai 对接多家协议，system 消息位置的支持不一；存储层不能把「系统消息在列表开头」当成前提。
- 运行期不重读 AGENTS.md（避免每个请求一次磁盘 IO）；变化感知以请求边界为粒度。

## 决策

- 统一 run / turn 生命周期钩子 `AgentLoopHook { prepareRun, prepareTurn }`：`prepareRun` 在每次 run 开始、用户消息进入历史与落盘之前触发；`prepareTurn` 在每次模型请求之前触发。同一时机的钩子按注册顺序串行执行，单个钩子抛错只记日志、不中断 run。`BeforeRequestHook` 随之移除，压缩迁移为 `prepareTurn` 内置钩子（本条的钩子机制取代 ADR 0004 的 `beforeRequest` 检查点机制）。
- 系统提示词刷新是内置钩子（`prepareRun` 与 `prepareTurn` 都挂）：重新装配后与最后一条系统消息逐节对比指纹；无变化则不动作，有变化或无基线就追加一条**完整快照**的系统消息并立即落盘。内置钩子的注册顺序保证刷新先于压缩，压缩总能看到刷新后的列表。
- 构造管线按节装配：内置节 identity / tools / project_context / cwd 都是 `PromptSectionProvider`；节声明 `freshness`（`construction` 只求值一次并缓存，如 project_context；`per-refresh` 每次装配重算，如 tools）。extension 未来以注册命名节的方式修改系统提示词。
- 系统消息携带 `sections` 元数据（节名 → 内容指纹）并随消息落盘，作为下次刷新与 resume 后的对比基线；老格式条目没有该字段，视为无基线（恢复后首个 run 必追加一条新系统消息）。
- 存储层（内存与会话文件）允许任意多条系统消息，按生产顺序追加；发给 provider 时在 loop 层生成发送视图：只保留最后一条系统消息并移到开头，其余消息保持原序。该投影与 provider 无关，`toPiContext` 不变。
- `Agent` 构造函数不再预建系统提示词；恢复会话按文件内容重放，漂移由首个 `prepareRun` 的刷新处理。恢复投影始终包含文件中最后一条系统消息（即使它在压缩保留区间之外），充当刷新基线，避免恢复后重复追加相同的一条。
- 压缩适配：系统消息与旧摘要消息不进可摘要区间（摘要侧信道永远不含系统消息）；压缩投影 = 最新系统消息 + 摘要 + 保留区间，旧系统消息从运行时投影丢弃，会话文件保留原文。token 估算（压缩阈值、状态栏）以发送视图为准。

## 后果

### 收益

- 新增工具、升级 CLI 后 resume 老会话、未来 MCP / Skill 中途接入，都能在最近一个请求边界被会话感知，无需新开会话。
- 每条系统消息是带节指纹的完整快照：盘上可审计「当时用的是哪份提示词」，diff 不需要重放历史。
- 发送视图集中在 loop 层一次实现，未来接非 pi-ai 的 provider 不必重新实现这套系统消息语义。
- 钩子机制统一了请求前检查点：压缩与刷新走同一通道，后续生命周期需求直接注册即可。

### 代价

- 消息列表不再隐含「`messages[0]` 是唯一系统消息」：压缩、恢复、token 估算都要按「任意位置、任意多条系统消息」处理。
- 运行期对 AGENTS.md 的修改不会被感知（按决策只在新会话 / 重启时重读）。

### 其他影响

- 新版写出的会话文件含系统消息条目；旧版本恢复这种文件时会把它们当普通消息透传进上下文，与旧版自建的系统消息并存（行为有偏差但不崩溃）。项目未发稳定版，与 ADR 0004 一样不保证旧版读新文件。

## 备选方案

### 方案 A: 变化时原地替换旧系统消息，不追加

- 优点：内存里恒为一条系统消息，不需要发送视图与压缩适配。
- 缺点：JSONL 是 append-only，「替换」在盘上仍要追加记录，存储与内存语义分裂；丢失「当时用了什么提示词」的审计链。
- 未选择的原因：与 append-only 一致性假设和审计需求冲突。

### 方案 B: 「只取最新系统消息」放在 `toPiContext`（协议适配层）

- 优点：改动集中在一处。
- 缺点：绑定 pi-ai 通道，未来非 pi 的 provider 要重新实现；存储与发送的差异是 agent 层语义，不属于协议适配层。
- 未选择的原因：loop 层一次实现，所有 provider 复用。

### 方案 C: 分节增量追加，发送时跨多条系统消息合并各节

- 优点：落盘数据量小。
- 缺点：「最后一条系统消息」不再是完整提示词，发送视图与恢复投影都要实现节合并，复杂度显著更高。
- 未选择的原因：完整快照自描述，变化检测靠节指纹已经足够。

### 方案 D: extension 用自由字符串 transform 链修改提示词

- 优点：最灵活，可改写任意内容。
- 缺点：transform 可改写任意节，节级指纹失去来源意义，顺序控制弱。
- 未选择的原因：命名节 provider 与分节 diff 自洽；未来确有全文改写需求时可再加兜底 transform。

### 方案 E: 文件 watcher / 注册表事件驱动刷新

- 优点：变化即刻感知。
- 缺点：引入 watcher 生命周期与运行期磁盘 IO；请求边界刷新已覆盖实际用例。
- 未选择的原因：运行期不重读 AGENTS.md 是明确决策，刷新点固定在 `prepareRun` / `prepareTurn` 更简单。
