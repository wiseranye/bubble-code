# 改用全屏（备用屏）模式

工具消息的头部要支持点击展开/收起，这需要鼠标事件。pi-tui 的主屏渲染器 `TuiMainScreen` 从不解析鼠标序列：只有 `TuiAltScreen` 会解析 SGR 序列、按布局树把事件派发到组件（0.85.1 的 dist 如此，上游 v1.2.0 也如此，主屏那条路径至今没有鼠标实现）。pi 自己的默认形态同样是全屏（`tuiMode: "fullscreen"`），所以 bubble-code 从 `TuiMainScreen` 切到 `TuiAltScreen`，并显式开启鼠标。转录区（横幅 + 消息区）放进 `ScrollView`（跟随底部、滚轮可滚），输入框、生成状态、提示行组成底部固定区，用 `VStack` 钉在视口下沿。

**考虑过的选项**：保留主屏，改用键盘（如 `Ctrl+O`）切换工具消息的展开——键盘不需要鼠标支持，但用户否决了该方案，坚持点击展开；继续等上游给主屏补鼠标支持——没有排期，且第三方依赖内部的渲染器不归我们改。

**后果**：转录内容不再留在终端 scrollback 里，翻看历史只能靠视口滚动（滚轮、`PgUp`/`PgDn`、`Home`/`End`），而不是终端自身的回滚缓冲；退出时用 `stop({ preserveScreen: true })` 直接切回普通屏（pi 在全屏模式下的做法），不在终端上留对话。鼠标点击、滚轮滚动、文本选择、`Ctrl+Shift+F` 搜索都归 pi-tui 的视口所有。组件要接住点击必须先处理 `press`：全屏渲染器只把处理过 press 的组件记为点击目标，再在 release 时补发 `click`，`ToolMessageView` 的展开/收起就挂在这条链上。ADR 0001 里"消息完成后不再修改"的理由（主屏对视口上方行的改动会整卷重打）在全屏下不再成立：每帧差量绘制，改动已冻结的工具消息只影响当前视口；`seal()` 的纪律仍然保留，但已不是硬约束。
