# 引入 pi-ai 接管 LLM 对接，项目只保留适配层

自研的 OpenAI 兼容对接（`src/llm/api/openai-completions.ts`）要持续跟进各家协议的流式格式、reasoning 的非标准 delta 字段（`reasoning`/`reasoning_content`/`reasoning_text` 探测）、usage 与 prompt cache 等能力，维护成本随接入协议数线性增长。我们把 LLM 协议对接交给 `@earendil-works/pi-ai`，项目只保留一层适配器 `PiModelApi implements ModelApi`：自有 `AgentMessage` 仍是协议历史、session 持久化与 UI 的唯一模型，适配层负责 pi ↔ 项目之间的消息双向转换与流事件重命名；请求绕过 compat 和 Models API，直调 pi 的 `api/*` 模块（官方文档认可的 bypass provider auth 路径，适配配置全在自己手里的场景），settings 配置装配成 pi 的 `Model` 时按 provider 名查 builtin catalog 兜底、settings 显式字段覆盖（catalog 自带更准的元数据和上游调好的兼容标志如 `thinkingFormat`，无成本数据的模型 `cost` 填零）；usage（含 cost）随 `AssistantMessage.usage` 落类型（UI 暂不展示），reasoning 以档位（`minimal`/`low`/`medium`/`high`/`xhigh`/`max`，缺省为不干预模型默认）接入，`cacheRetention` 硬编码 `'short'`。

**考虑过的选项**：全链路换 pi 原生类型（`Context`/`AssistantMessage`），少一层转换，但 session 落盘格式、恢复逻辑、UI 全部要改，旧会话还要迁移——CONTEXT.md 里协议消息是项目领域模型，为省一层转换而动它不值得；compat 入口的 `stream`/`streamSimple` 最省事，但该入口整体已 deprecated，上游注释明说会随 ModelManager 迁移删除；`/models` 新 API（`createModels`/`createProvider`）官方支持自定义 provider，但要求把 provider 注册进其 catalog 流程，per-request `apiKey` 直传对本项目更直接。

**后果**：settings 的协议枚举对齐 pi 命名（`anthropic` → `anthropic-messages`），`reasoning` 从布尔变档位枚举，`input`/`maxTokens`/`contextWindow` 去掉默认值变 optional——否则无法区分「没写」（跟随 catalog）与「显式覆盖」；既有配置文件需手工迁移，项目未发稳定版，不留向后兼容。pi 的 `error` 事件只携带 `AssistantMessage`（错误文本在 `errorMessage`），适配层负责包成 `Error`；`toolcall_start` 不带完整对象，聚合到 `toolcall_end` 才发出项目的 `tool_call_end`；`stopReason` 的 `deferred`（长任务挂起）项目无此概念，映射为 `stop`。Thinking block 的 `thinkingReplayData` 语义变为存 pi 的 `thinkingSignature`；旧 session 文件里该字段存活的是 provider delta 字段名，仅对 anthropic 协议有理论影响，而旧会话不可能是 anthropic（协议刚引入），无实际回归。图片输入、env var 展开、oauth、catalog 的动态模型列表（`fetchModels`）均不在范围内。
